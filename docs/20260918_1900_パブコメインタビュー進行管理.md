# AIパブコメ10件の進行管理

## 役割分担

- サーバーがテーマ順、固定前提、短い固定質問、深掘り回数、終了を決定する。
- AIは受け止めと指定テーマの深掘り質問を生成する。説明依頼・安全対応・辞退・対象者判定も構造化出力で返すが、任意のテーマIDや終了先は指定できない。
- 元の固定質問全文は各 `shared/campaign.ts` に残す。表示用の短い前提・問いは `shared/question-presentations.ts` に70問分を管理する。全文の読み上げや、深掘りごとの前提の繰返しは行わない。

## 3方式

| 設定 | 進行 |
| --- | --- |
| loop（全10件の初期設定） | 固定質問 → 深掘り1 → 深掘り2 → 次の固定質問 |
| bulk | 全固定質問 → 各テーマの深掘り1・2 |
| targeted | loopと同じ。設定された対象条件を本人の明示的な発言で評価し、対象外なら内部に保存して次へ |

通常の完了には7テーマ×3回答が必要。深掘りを「出した回数」ではなく「回答を受けた回数」を保存する。
対象条件不明は対象外にしない。病気・障害・性別等の推測を禁止する。判定と根拠メッセージIDはサーバー内部にだけ保存し、画面・APIには返さない。targetedでは残り数や進捗率からスキップを推測できない表示とする。

既存70問は広く意見を伺う内容なので、対象条件を勝手に新設しない。現状 `target_audiences={}` ではtargetedも全問対象。実際の除外を行う場合は、運営側が質問ごとに明確な条件を設定する。

## 運営設定

`public_comment_campaigns.interview_mode` で3方式を選ぶ。
`target_audiences` は質問IDから対象条件の文章へのJSONオブジェクト（例: `{"experience":"介護の仕事に従事している人"}`）。実際に存在する質問IDだけを指定する。
設定UIは今回追加していない。管理権限のあるDB操作で設定する。設定したmodeと対象条件は開始時にsessionへ保存し、既存の会話の途中で変更しない。

## 中断・移行・再送

- 「このテーマを飛ばす」または明示的な辞退では2回の深掘りを強制しない。「ここまでで終了する」も選べる。
- 説明依頼は回答回数に含めない。
- 安全案内が必要な発言は保存せず、中断状態にする。固定質問・深掘り・終了へ自動進行しない。本人が「意見整理を再開する」を選ぶまで継続しない。
- 既存セッションの回答済みテーマはやり直さない。未回答のテーマから新方式へ移行する。既に下書きがある場合は確認・編集へ戻る。
- sessionのrevisionとrequest UUIDで競合・二重送信を制御する。ユーザー発言、AI発言、進行状態、再送用の結果は一つのDBトランザクションで保存する。
- 通信断では同じrequest UUIDで再送する。不確かな送信が残った状態で別の回答を送ることは防ぐ。複数タブの競合は409で知らせ、再読込して再開する。

## 導入

コードとあわせて `20260918200000_public_comment_interview_progress.sql` の適用が必要。新しいAPIはrequest UUIDとrevisionを要求するため、更新前から開いている画面は再読み込みが必要。
本番DBへの適用や本番公開はこの変更のローカル検証とは別。会話・下書きの公開、区への送信、メールの同意仕様は変更しない。

## 検証

- 全10件×3方式の純粋関数テストと実DBによるHTTPハンドラー統合テスト。
- DB RPCの所有者・キャンペーン認可、並行送信、再送、トランザクション、完了後凍結、RLSの統合テスト。
- 通信断・連打・安全対応・スキップ・終了のReact hookテスト。
- 個別に重複していた旧session/chatテストは、共通実DBテストと全20ルートの配線テストへ集約。
- AIの応答はテストで差し替える。自然な深掘りの品質や判定内容の正確性を、決定論的な進行保証と混同しない。
