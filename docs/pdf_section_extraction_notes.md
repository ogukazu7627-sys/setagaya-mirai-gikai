## 結論

一般会計歳出の明細3 PDFページから、款・項・目・本年度予算額と、
節番号・節名称・節金額をOCRなしで抽出できた。抽出した39節行はすべて、
節金額合計が対応する目の本年度予算額と一致した。

今回のCSVは抽出可能性を確かめる中間形式であり、全ページを網羅する完成テーブル
ではない。`budget_programs.csv` との結合も行っていない。

## 抽出方法

実験スクリプトは
`packages/budget-data/scripts/extract_pdf_sections_sample.py` に置いた。
依存ライブラリは `pdfplumber==0.11.9` である。

1. PDFの埋め込みテキスト層を `pdfplumber` で抽出する。
2. 罫線を使った表検出で、左半分の款項目表と右半分の節表を分ける。
3. ページ上部の文字列から款と、記載されている場合は項を抽出する。
4. 左表の「目」列と「本年度」列から、目コード・名称・本年度予算額を抽出する。
5. 右表の「区分」「金額」列から、節コード・名称・金額を抽出する。
6. 複数の目があるページでは、左表の目の上端と右表の節行の上端を縦座標で
   比較し、直前の目へ節行を対応付ける。
7. 金額の桁区切りカンマを除去し、千円単位の整数にする。節名称内の改行は
   レイアウト上の折返しとして連結する。
8. 目ごとに節金額を合計し、本年度予算額との一致を検査する。

意図しない全ページ処理を避けるため、`--pages` は最大3ページに制限した。
既定の対象は `159,162,166` である。

```bash
python3 -m pip install \
  -r packages/budget-data/requirements-pdf.txt

python3 packages/budget-data/scripts/extract_pdf_sections_sample.py \
  --input raw/r8tousyoyosanallpage.pdf \
  --output processed/raw_pdf_sections_sample.csv \
  --pages 159,162,166
```

`parse_status=needs_review` とし、理由を `parse_note` に残す。

- 節番号・名称または節金額を解析できない
- 節行を目へ対応付けできない

`raw_text` には、節表から取得した区分セルと金額セルを正規化前の形で残した。

## 確認できた失敗パターン

今回の3ページでは全行を抽出できたが、周辺ページの確認から、全ページ処理には
次の問題がある。

- PDF 160・161ページのような款・項の集計ページには節行がない。見出しだけで
  明細ページと判定すると空データになる。
- PDF 163ページ以降には、前ページの説明や節行がページ上端から続くページが
  ある。単一ページだけでは款・項・目を確定できない場合がある。
- 説明列は複数の節行を縦にまたぎ、表抽出では先頭の節行へ説明全文が結合される。
  説明列を節ごとに単純分割することはできない。
- `使用料及賃\n借料`、`負担金補助\n及交付金` のように節名称が改行される。
- 1ページに複数の目がある場合、右側の節表は1つの表として抽出される。
  節コードは目ごとに繰り返すため、コードだけでは所属する目を判定できない。
- 款・項・目の文字列は、PDFの結合セルによって同じセル内に連続して抽出される
  場合がある。列位置、重複除外、縦座標を組み合わせる必要がある。
- PDFページ番号と冊子ページ番号が異なり、見開き1 PDFページに冊子2ページが
  含まれる。

## 今後の方針

全ページ処理へ進む前に、ページ状態を引き継ぐ抽出器が必要になる。

1. 一般会計歳出の開始・終了ページを明示し、集計ページと明細ページを分類する。
2. 款・項・目をページ間で引き継ぎ、継続ページの節行へ直前の目を割り当てる。
3. 罫線と縦座標による所属判定を基本にし、金額合計の一致を必須検証にする。
4. 不一致・継続元不明・表検出失敗を `needs_review` のレビューキューへ出す。
5. 款・項・目コードを使ってPhase 1の `budget_item_key` と突合し、PDF側の
   階層誤認を検出する。
6. ページ種別ごとのサンプルを増やして精度を測定した後に、全ページ抽出を行う。

### stateful extractorの処理

Phase 2.5のページ単位抽出器を全ページへ適用せず、次の状態を保持する
`StatefulSectionExtractor` を実装した。

- 現在の款 `current_kan`
- 現在の項 `current_kou`
- 閉じていない目 `current_moku`
- `current_moku` の本年度予算額
- `current_moku` に属する全節行とページ範囲
- 表検出失敗など、目が閉じるまで保持すべき原因コード

ページ内では、左表の目境界と右表の節行を縦座標順のイベントとして処理する。

1. 最初の目境界より上にある節行を、前ページの `current_moku` へ割り当てる。
2. 新しい目境界を検出した時点で、直前の `current_moku` を閉じる。
3. 新しい款・項・目で状態を更新し、以後の節行を新しい目へ割り当てる。
4. ページ末尾では目を閉じず、次ページへ状態を持ち越す。
5. 新しい目・項・款、または対象範囲の終端を検出した時だけ金額を検算する。
6. 節合計と目本年度予算額が一致し、ほかの原因がなければ全節を
   `parse_status=parsed` とする。
7. 不一致または解析上の原因があれば、その目の全節を
   `parse_status=needs_review` とし、`parse_note` に原因コードを残す。

説明欄だけが続くページでも `current_moku` を維持する。これにより、
説明が数ページ続いた後に次の目が始まるケースでも、直前の目を誤って
ページ末尾で確定しない。

### 164→165ページの回帰確認

| ---: | ---: | ---: |

| 165 | 3 | 250,052 |

### `needs_review` 原因コード

今回の出力では `needs_review=0` だった。今後別年度や異なるレイアウトで
問題が発生した場合に備え、stateful extractorは次の原因コードを持つ。

| 原因コード | 意味 |
| --- | --- |
| `moku_total_mismatch` | 目を閉じた時点で節合計が本年度予算額と不一致 |
| `section_value_parse_failure` | 節番号・名称または金額を解析できない |
| `continuation_without_current_moku` | 冒頭継続節に引継ぎ可能な目がない |
| `table_detection_failed_in_moku_span` | 開いている目の途中で表検出に失敗 |
| `hierarchy_context_missing` | 款または項を復元できない |
| `budget_book_page_missing` | 冊子ページ番号を復元できない |
| `moku_without_sections` | 目を検出したが節行がない |
| `duplicate_moku_key` | 同じ款・項・目コードが再度開始された |
